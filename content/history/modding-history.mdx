Blizzard never released official modding tools for Diablo II. The community built them anyway. Because so much of the game lives in data tables, a player with a spreadsheet and an MPQ tool could change drop rates, item stats and skills within months of launch.

## The data tables

The first mods were table edits. Players pulled the TXT files out of the MPQs, changed values, and loaded them back in. Figuring out what each column did took years of collective testing. The results were written up in community file guides, many of which survive only in archives today.

## The Phrozen Keep

The Phrozen Keep became the centre of Diablo II modding. Its forums and knowledge base held file guides, tutorials, tool releases and whole mod projects. A great deal of what's known about the game's files was first documented there. It has [its own page](/history/phrozen-keep).

## Code modding

Table edits have limits. To add new mechanics, modders had to change the game's code. Through reverse engineering, they learned to patch the game's DLLs and hook into its functions. This let mods add features the tables couldn't express, and it produced plugins that other mods could share.

## Patch baselines

Mods had to pick a patch and stick with it, because code mods depend on exact memory addresses. 1.09 and then 1.10 were long-lived baselines. Later, 1.13c became the standard. When 1.14 merged the DLLs into `Game.exe`, most of the scene stayed on 1.13c instead of rebuilding everything.

## Today

Modern modding combines the old knowledge with open-source research. Projects that reconstruct the game's code make it far easier to understand what the game does. Large projects such as [Median XL](/mods/median-xl), Project Diablo 2 and Path of Diablo show how far the engine can be pushed.
